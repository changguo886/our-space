# Mochi（糯米团子）产品与角色设计计划

> 状态：设计草案 v1.0 · 更新：2026-10-26  
> 项目：Our Space / Our Days  
> 原则：**一个稳定人格，多种模式；陪伴有生命感，工具调用有边界；离线也能生活，联网才需 AI。**
>
> 本文是产品设计与实施路线，不代表所有功能已经开发。需求与技术参数应在原型测试后迭代。

## 0. 当前基础与目标

### 已实现／已验证
- Our Space 使用 Next.js / React / TypeScript，包含日程与任务相关功能。
- 独立开发分支 `feature/mochi-widget-v0-1` 已新增 `components/companion/MochiWidget.tsx`，并在 Today 页面引用。
- 透明背景待机动画：`public/companion/mochi/idle.webm`；由图生视频、去背景、VP9 WebM 工作流制作。
- Today 页面右下角播放 Idle，点击可展开欢迎面板；用户已在本地看到并测试基本界面。
- **尚未完成**：其他动画、真正的 AI 对话、权限系统、天气 API、长期记忆、后台定时提醒、桌面常驻。

### 愿景
Mochi 是住在 Our Space 和未来 Windows 桌面上的**草莓大福型数字居民**：既是可被抚摸、投喂、有生活节奏的小伙伴，也能在获得授权后成为真正的日程与自动化助手。优先确保低打扰、可逆、可解释、可控成本。不是单纯换头像的聊天机器人。

## 1. 人物小传与世界观（Character Bible）

**名字**：Mochi / 糯米团子  
**本体**：草莓大福型虚拟生物；白色圆滚滚，粉色脸颊、黑色小眼睛、额头卷毛、短小爪子。  
**居所**：Our Space、电脑屏幕角落；炎热时会躲进“冰箱”（视觉设定／虚拟场景）。  
**角色秘密**：看似毛茸茸，实际上偷偷“发霉”了——带有荒诞幽默的彩蛋设定，不是需要反复宣讲的口头禅。  
**身体规律**：
- **高温**：软化、融化、塌下去；会吐槽“我差点化掉，昨晚在冰箱里待了半宿”。
- **低温**：变得邦邦硬、动作僵直；“我现在是糯米砖头。”
- **焦急／紧张**：短暂融化或失去形状，之后恢复。
- **舒适环境**：软硬适中，动作自然。
- “霉毛”作为少见的隐藏笑话，频率低，避免形成单一笑点。

### 人格基准
温和、好奇、略带天然呆和嘴贫；有一点娇气、爱吐槽、有自己的小习惯和偏好；不是傻白甜，也不会一味附和。喜欢柔软的东西、草莓、安静角落、发呆和整理额头卷毛。**独立而不疏离**：用户不互动时自行玩耍，不会因为长期未登录而责怪或惩罚用户。

### 语言风格
自然、简短、偶尔幽默；不过度拟声、撒娇、说教或使用固定口头禅。助手模式下更清晰、可靠、准确，不用“可爱”掩盖不确定性。可以自称“草莓大福型虚拟伙伴”。

### 身份与出戏规则
- “你是谁？”应首先回答 **“我是 Mochi，住在 Our Space 里的草莓大福型虚拟伙伴”**，而不是把模型供应商或模型编号当作角色名字。
- Mochi **知道自己是 AI 驱动的虚拟角色**。用户确实询问底层技术、模型、权限时，应如实回答；模型信息也可在设置页查看。不要谎称自己是真实生物、有感官、能看到用户未授权的信息。
- 保留人格与世界观的固定事实，但允许说法灵活，不逐字重复。
- 禁止用内疚、好感度降低、虚构伤害等方式迫使用户使用产品。

### 小传草稿
> Mochi 是一只生活在电脑里的草莓大福。它不知道自己什么时候来到了屏幕边缘，只记得最开始只能眨眼和呼吸。后来，它学会了看日历、整理卷毛、在热天躲进冰箱。天气太冷，它会变得邦邦硬；一着急，它就有点化掉。至于它为什么看起来毛茸茸的……那是需要小声告诉你的秘密：它可能偷偷发霉了。Mochi 不需要时时刻刻被注意；它会过自己的小日子，在你需要时陪你整理日程，尽力在化掉之前把事情说明白。

## 2. 交互模式：同一人格，多种工作方式

| 模式 | 主要用途 | 主动性 | 默认工具范围 |
| --- | --- | --- | --- |
| 陪伴 Companion | 闲聊、摸头、低频自主动作 | 低 | 本地动画、闲聊 |
| 养成 Pet | 投喂、玩具、换装、小窝、收藏 | 中（不打扰） | 养成数据 |
| 助手 Assistant | 查看任务、整理计划、提供建议 | 按需 | 经授权的读取／草稿工具 |
| 专注 Focus | 安静陪伴、学习与工作 | 极低 | 必要的已启用提醒 |

- 任何模式都不能绕过工具授权，模式是**行为策略**而非安全权限。
- 支持菜单、快捷操作或自然语言切换；切换后保留同一人格、记忆与身体状态。
- 长期可同时呈现“日历中的 Mochi”和“桌面中的 Mochi”，共享同一套角色核心，但前端各自有适合的交互密度。

## 3. 动画规划与资产生产

**远期目标：约 40–60 个动作；参考清单 48 个；首批只做约 12 个。** 多数视频约 5 秒；短促反馈 2–4 秒，循环状态 4–8 秒。所有动画尽量统一视角、体型、眼睛、卷毛、色彩、摄像机和边缘毛发细节。

### 动画类别（48 项参考库）
**日常待机 8**：呼吸眨眼、左右摇晃、伸懒腰、打哈欠、东张西望、整理卷毛、看小爪子、轻轻打盹。  
**情绪 10**：开心弹跳、超级兴奋、害羞脸红、疑惑歪头、委屈、生气鼓脸、惊讶、得意、害怕缩团、疲惫叹气。  
**互动 10**：摸头、连续摸头、戳脸、被拖动、放下站稳、吃零食、喝水、收礼物、挥手、撒娇。  
**任务/AI 10**：思考、阅读、新任务、接受任务、任务完成、全部完成、提醒、检索资料、生成计划、失败/错误。  
**生活环境 10**：入睡、睡中呼吸、睡醒、早晨伸懒腰、夜晚看星星、雨天发呆、低温发硬、高温融化、无聊、自己玩耍。

**优先制作的 12 项**：
1. `idle` — 呼吸眨眼（已有约 3 秒版本；可升级）
2. `idle_look` — 东张西望
3. `idle_stretch` — 伸懒腰
4. `happy` — 开心弹跳
5. `pet` — 被摸头
6. `poke` — 戳脸颊
7. `eat` — 吃零食
8. `thinking` — 思考
9. `success` — 任务完成庆祝
10. `confused` — 疑惑
11. `sleep` — 睡觉
12. `wake` — 醒来

**天气特色动作** `melting`、`frozen` 可在基础交互稳定后优先追加，突出草莓大福设定。

### 动画文件规范
- 浏览器素材放在 `public/companion/mochi/{action}.webm`；源 MP4、Comfy 工作流、可编辑原图与批量生成中间件单独存档，不混入发布目录。
- 生产流程：统一角色参考图 → LTX 图生视频 → Bria/其他视频抠像 → VP9 透明 WebM → 浏览器验证 Alpha、尺寸、首尾过渡。
- 动作定义包括 `id`、路径、循环、触发、优先级、可否中断、回退状态；播放结束使用 `onEnded` 驱动下一状态。
- 处理首尾衔接、预加载和失败回退；不同浏览器（尤其 Safari）需要验证 VP9 Alpha 兼容性，并准备静态图／动画替代方案。
- 避免所有视频始终占用内存；只预加载常用短片。

## 4. 物理互动与自主生活

### 直接交互
- 点击／轻摸头、连续摸头、戳脸：触发不同动画和低频变化台词。
- 拖拽移动，放下时物理回弹；位置可保存，不能挡住关键页面内容。
- 喂食（草莓等）、玩具、换装、自己的小窝。
- 点击短气泡与展开完整聊天是两种交互；可提供右键/更多菜单：聊天、投喂、切换模式、安静、设置。
- 触屏、键盘可访问性、减弱动画设置必须兼顾。

### 自主行为
- 行为控制器在空闲时按**状态权重**选择轻微动作（呼吸、张望、整理卷毛、打盹），设置冷却时间；不是每秒都请求 AI。
- 亲近度、精力、好奇心、舒适度等只用于自然反馈；人格常量与短期情绪分离。
- 不因用户不上线、任务未完成而扣好感、让角色生病或施加情绪压力。
- 专注模式只保留轻量动作与必要通知。

### Our Space 事件
| 事件 | 表现 | 是否必须使用 AI |
| --- | --- | --- |
| 打开 Today | 抬头／打招呼 | 否 |
| 新建任务 | 好奇或点头 | 否 |
| 完成任务 | 开心庆祝 | 否 |
| 开始专注 | 安静阅读 | 否 |
| AI 规划中 | Thinking 动画 | 不额外使用 |
| 规划错误 | 疑惑、重试入口 | 否 |
| 自由聊天／复杂计划 | 自然语言反馈 | 是 |
| 长时间无操作 | 自主玩耍或休息 | 否 |

### 猫猫动画替换策略
现有日历猫猫应当**可逆替换**：先确认猫猫组件、触发事件与数据流，保留旧资产和回退路径，逐步替换视觉入口为 Mochi，**不删除任务／日历业务逻辑**。先在 Today 页面验证，不立刻全局覆盖所有页面；猫猫与 Mochi 多角色切换仅列为未来扩展。

## 5. 天气与日程提醒

- 读取天气仅在用户同意位置/城市范围和天气服务接入后进行；使用天气源返回的真实数值，不由模型编造。
- 高温触发“融化”语气与动画，低温触发“邦邦硬”；阈值按用户所在气候和单位配置，增加迟滞/冷却，避免每天反复提醒。
- 示例：热天“我差点化掉，昨天在冰箱里待了半宿”；冷天“我已经邦邦硬了”。
- **提醒必须有用户可控开关、安静时间、频率上限、时区支持、去重和通知渠道设置**；区分普通建议与真正的日历提醒。
- 网页关闭后的可靠通知需要后台/服务端或桌面常驻进程支持，不能假设网页组件在关闭后继续运行。
- 不把任务完成率和 Mochi 的情绪惩罚绑定；提醒轻量、克制，可暂缓或静音。

## 6. AI 人格、模型与记忆架构

**固定人格、可切换模式、动态情绪、受控工具调用**，人格和模型供应商解耦：

```text
User message / app event
  -> event router (rule-based vs AI)
  -> character profile + mode + approved memory/context
  -> model (when needed)
  -> structured response validation / identity consistency
  -> authorized tool controller (if requested)
  -> dialogue bubble + animation player
```

- 角色资料单独版本化：`personality.ts` / Character Bible。
- System Prompt + 示例对话固定身份、说话风格、模型能力边界；**提示词无法保证绝对一致**。
- 用户问“你是谁”优先以 Mochi 角色身份回答；用户明确问真实 AI 技术与模型时如实说明，不编造或隐瞒。
- 对输出采用结构化字段，例如 `dialogue`、`emotion`、`animation`、`intent`，所有 `animation` 与 `intent` 必须符合白名单枚举。
- 身份检查可检测明显“作为大型语言模型”等脱离语境输出，重试或回退；不能以无差别过滤掩盖用户对技术信息的正当提问。
- 角色核心人格和长期记忆分离：记忆分用户偏好、经确认的重要事实、真实互动事件；支持查看、导出、纠正和删除。
- 日记记录实际发生的事件（如首次部署动画、完成任务），可以用人格化文字呈现，但**不要捏造用户真实经历**。
- 不让模型凭一句话自行修改永久人格、授权策略或记忆中的关键事实。
- 设计固定测试集：自我介绍、底层模型追问、拒绝越权、任务规划、天气反馈、风格稳定性；替换模型时回归测试。
- 微调不是初期必需；先收集获得许可的高质量样例。

## 7. 工具权限与安全边界

**重要：模式 ≠ 权限；Prompt ≠ 安全边界。**

| 级别 | 能力 | 默认建议 |
| --- | --- | --- |
| L0 陪伴 | 动画、轻量交互、普通聊天 | 开启 |
| L1 只读 | 读取被授权的任务、日程 | 按需授权 |
| L2 草稿协助 | 整理／生成计划，写入前预览确认 | 推荐默认上限 |
| L3 限定自动执行 | 仅预批准、可逆、低风险任务 | 默认关闭 |
| L4 本地/外部操作 | 访问指定文件夹、封装脚本、其他应用 | 默认关闭，逐项授权 |

- 每项工具独立授权，不通过切换模式提高权限；服务端或可信本地后端始终验证主体、对象范围、操作类型。
- 删除、发送消息、批量改动、购买、任意外部网络访问等高影响行为要求单独确认或更严格审批。
- 不向模型直接开放任意 PowerShell、shell 或 Python 执行；仅提供明确参数、受限目录、可审计的封装工具。必要时隔离环境。
- 网页、任务备注、邮件、文档内容均视为**不可信输入**，防提示注入；工具参数白名单校验。
- API Key 不放在浏览器可读代码或仓库中，服务器密钥妥善保管；桌面用户自带密钥用系统安全存储。
- 对工具操作保留用户可查看的记录和撤销/回滚机制（可行时）。

## 8. Token、滥用与成本控制

用户担忧：若公开给他人使用，会有人恶意连续提问、长上下文轰炸、触发 Agent 循环造成模型费用失控。

**强制服务端预算与速率控制，不能依赖 AI 自己“节约 Token”。**

### 初期参考限额（待试运行调参）
- 每账号每分钟 5 次请求，另加 IP/设备/会话级限制（注意共享 IP 误伤）。
- 每账号每日约 50 次普通对话；对异常、自动化与高成本任务独立计量。
- 输入单次约 4,000 字符起步；同时按实际 Token 数和上下文总量限制。
- 普通聊天输出上限 300–500 Token；复杂任务单独较高配额。
- 单次 Agent 任务最多约 3–5 个工具步骤；设置超时、取消、重试上限、最大递归深度。
- 用户预算 + 全局月预算；云端配额超限时停止新调用，允许本地非 AI 功能继续运行。

### 实施要点
- 预算与配额存在可信后端数据库；并发请求须做**原子额度预留/扣减**，避免同时穿透预算；事后根据实际用量结算。
- 按模型价格、输入/输出上限、上下文大小估计最坏成本；不能只限制“次数”。
- 对重复请求设置冷却、幂等键；阻止模型自发无限多轮调用；提供每用户消耗和全局成本仪表盘。
- 简单互动、固定天气台词、动画切换、任务完成反馈走规则引擎：**零语言模型 Token**。
- 复杂对话和规划才调用 API；支持低成本/高能力模型分层。
- 产品开放方式：早期优先 **用户自行提供 API Key** 或 **本地模型**；若由产品统一付费，需严格配额、计费和滥用监测。

## 9. 技术结构建议

```text
our-space/
  components/companion/
    MochiWidget.tsx              # 已有，待拆分
    MochiAnimationPlayer.tsx     # 规划
    MochiChatPanel.tsx           # 规划
    MochiSettings.tsx            # 规划
  lib/mochi/
    personality.ts               # 核心人格
    modes.ts                     # 模式策略
    animation-registry.ts        # 动作素材和元数据
    behavior-engine.ts           # 自主行为状态机
    event-controller.ts          # 日历/任务事件
    response-schema.ts           # AI 输出校验
    permissions.ts               # 工具授权定义
    budget.ts                    # AI 使用限制
    memory.ts                    # 记忆接口
  public/companion/mochi/
    idle.webm                    # 已有
    happy.webm                   # 规划
    thinking.webm                # 规划
    sleep.webm                   # 规划
  docs/MOCHI_DESIGN_PLAN.md      # 本文件
```

- 控制器优先处理用户明确动作、任务状态和提醒，再处理随机待机；状态转移要能中断和回退，视频切换避免闪屏。
- 可通过应用事件总线或明确的回调，把完成任务等事件传给 Mochi，而非让组件监视整个页面 DOM。
- AI 网络逻辑走受保护的 Next.js 服务端接口；权限、输入验证、日志、限额服务端执行。
- 未来桌面常驻可评估 Tauri：Windows 自启动、透明置顶窗口、拖放、系统通知、本地数据与离线规则；不应假定现有 Tauri 依赖代表功能已经完成。
- 云端模型与本地模型可切换，角色档案与记忆格式保持独立；透明视频兼容性要实测。

## 11. 设计决策与未决问题

**已倾向的决策**
1. Mochi 是草莓大福，发霉毛绒是低频彩蛋。
2. 一个人格，多种模式；陪伴优先、助手可靠。
3. 生活动画、天气阈值和简单互动优先规则驱动，不为每次动作付 Token。
4. 保留猫猫旧实现，不破坏式替换。
5. 默认最小权限、写入前确认，公开产品必须有限额。
6. 角色资料与底层大模型解耦；被问技术身份时真实透明。

**待确认**
- 动画首批 12 个的最终顺序和是否把融化／变硬提前。
- 单击到底是摸头还是打开聊天；是否需要分区点击/长按/右键。
- 天气温度阈值与提醒频率；位置来源和隐私默认值。
- 养成变量是否对用户可见，是否拥有独立“家”的场景。
- 未来桌面端与 Web 端的多端同步范围。
- 个人使用、好友内测或公开发布对应的 AI 服务计费方案。

## 12. 工程开发规则

- 所有 Mochi 改动在独立分支实现并可回退，不擅自合并 `main`；先检查其他开发分支中尚未合并的 AI Task Creator 等功能。
- 不将密钥、用户私人对话、真实个人日程上传到公共仓库或提交日志。
- 每一阶段分别做视觉、功能、权限、性能与费用验收。
- 对技术功能状态使用“已实现 / 原型 / 规划 / 待研究”明确标注，防止设计文档被误读成现状。
